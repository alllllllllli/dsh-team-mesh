- 适用：Windows 10+（本手册在 mcloud / PowerShell 5.1 上走过）、DSH 桌面包（Electron 安装版）
- 基准事实：**2026-11-15 host-check**（独立验证者）用本手册的方法实跑；报告
  `C:\Users\Admin\work-20261115\hostcheck\report.md`，证据 `...\hostcheck\evidence\`（含 `README.md` 索引）。
- 一句话结论：**激活层已验证**（真实宿主启动、插件被激活、`apply()` 跑完、`src/spec.js` 实测 13 个工具）；
  **宿主工具注册表级 / 模型侧工具目录未直接观测**（CLI 不导出 info 日志，本次也没有模型调用）。
  详细边界见文末 §9。

## 1. 启动入口（`dsh` 不在 PATH）

真实入口是**安装目录自带**的 CLI 包装脚本：

`<安装目录>\resources\runtime\cli\bin\dsh.cmd`

它做的事（原文）：

```bat
@echo off
setlocal DisableDelayedExpansion
set "ELECTRON_RUN_AS_NODE=1"
"%~dp0..\..\..\..\DeepSeek Harness.exe" --expose-internals "%~dp0..\..\..\app.asar\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\cli.js" %*
exit /b %errorlevel%
```

即：用 **Electron 可执行文件当 Node 跑 `app.asar` 里的 `dsh-desktop-host/lib/cli.js`**，
且必须带 `--expose-internals`。所以「dsh」= 安装目录 + `ELECTRON_RUN_AS_NODE=1` + 这个 cli.js。

### 隔离启动命令（宿主，随机端口、仅回环、不打开浏览器）

```powershell
$install = 'C:\Users\Admin\AppData\Local\Programs\DeepSeek Harness'
$home    = 'C:\Users\Admin\work-20261115\hostcheck\dsh-home'   # 隔离 DSH_HOME，别指向真实 ~/.dsh
New-Item -ItemType Directory -Force -Path $home | Out-Null

$env:DSH_HOME            = $home
$env:ELECTRON_RUN_AS_NODE = '1'

& "$install\DeepSeek Harness.exe" --expose-internals `
    "$install\resources\app.asar\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\cli.js" `
    hostcheck --no-open --port 0 --host 127.0.0.1
```

- `hostcheck` 是**profile 名**（在 `$DSH_HOME\profiles\hostcheck`）；
- `--port 0` 让系统挑空闲端口；实际端口看 stdout 的 `dsh web: http://127.0.0.1:<port>/?token=…`；
- `--host 127.0.0.1` 只绑定回环，**别**用 `0.0.0.0`；
- **stdout 打印的 URL 里含访问 token，属敏感信息**：复制进日志/证据前必须替换成 `token=<redacted>`。
- 等价简写：`& "$install\resources\runtime\cli\bin\dsh.cmd" hostcheck --no-open --port 0 --host 127.0.0.1`
  （`dsh.cmd` 自己会设 `ELECTRON_RUN_AS_NODE=1`，`--expose-internals` 也在里面）。

> 不要用真实 `~/.dsh` 做这些实验；也不要在用 DSH 没停时把 `DSH_HOME` 指过去。

## 2. 隔离 profile 组装（`link:` + bundles）

### 2.1 从 shipped `web` 模板造 profile 骨架

宿主 CLI 自带 `--from-default-profile <name>`（见 `dsh --help`：用 shipped profile 模板重建一个自定义 profile）。
`--help` 只打印应用帮助、不真正启动服务，适合"只建骨架不跑"：

```powershell
$dshCmd = "$install\resources\runtime\cli\bin\dsh.cmd"
& $dshCmd hostcheck --from-default-profile web --help
```

生成 `$DSH_HOME\profiles\hostcheck\`：

| 文件 | 作用 |
| --- | --- |
| `package.json` | profile 依赖与 `dsh.profile.bundles`（模板默认 `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-web-app`） |
| `cordis.yml` | profile 根（模板是空列表，**不要**编辑它） |
| `cordis.patch.yml` | **本 profile 的用户补丁层**（顶层 YAML 数组；id 定向的 config 覆盖 / disable / insert）——插件配置写这里 |
| `pnpm-workspace.yaml` | `nodeLinker: hoisted`、`autoInstallPeers: false`（`dsh plugin add` 用 pnpm 时生效） |

### 2.2 把 mesh 以 `link:` 装进来

本次隔离环境的最终形态（可手工复现，也是 `dsh plugin add` 的产物形态）：

```powershell
$prof = "$home\profiles\hostcheck"

# ① package.json 的 dependencies 记 link:
#   "dsh-team-mesh": "link:C:/Users/Admin/dsh-plugins/dsh-team-mesh"
# ② node_modules 里放 junction 指向干净 0.4.0 包（不要拷副本，避免"源/装不一致"）
New-Item -ItemType Directory -Force -Path "$prof\node_modules" | Out-Null
New-Item -ItemType Junction -Path "$prof\node_modules\dsh-team-mesh" `
  -Target 'C:\Users\Admin\dsh-plugins\dsh-team-mesh' | Out-Null
# ③ bundles 里加 "dsh-team-mesh"
```

等价 CLI 用法（宿主文档示例 `dsh plugin --profile <name> <pnpm-args>`）：

```powershell
& $dshCmd plugin --profile hostcheck add "link:C:/Users/Admin/dsh-plugins/dsh-team-mesh"
```

> 该命令底层是 pnpm；**离线/无缓存环境先确认 pnpm 可用**（本次 host-check 的最终形态是
> 「dependencies 为 link: + node_modules 为 junction」，没有依赖联网安装 mesh）。

### 2.3 必须再装 `dsh-interconnect`（见 §3 的坑）

模板注释原文：*"a top-level YAML array of loader patch entries (id-targeted config overrides,

## 3. 坑：`inject = ['tools','interconnect']` 是**硬激活依赖**

`dsh-team-mesh` 的 `dsh.plugin.json` 声明 `inject: ['tools','interconnect']`。
**只装 mesh、没装 interconnect** 时，宿主不会激活插件，也不会注册任何工具，stderr 会给出明确诊断：

```
dsh: warning: 1 entry did not activate
dsh-team-mesh (dsh-team-mesh): pending (waiting for service: interconnect)
```

（证据：`evidence\host-pending-no-interconnect.err.log`；这个 run 的 stdout 只有 web URL。）

补上 `dsh-interconnect`（并进 bundles）后：插件激活、**stderr 0 字节**
（证据：`evidence\host-loaded-fake-dispatcher.err.log`、`host-loaded-empty-dispatcher.err.log`）。

> 所以：**pending 不是"慢"，是缺依赖**。看到 `pending (waiting for service: …)` 先查
> `dsh.plugin.json` 的 `inject` 与 profile 里对应 bundle 是否都在。

## 4. 怎么判断"插件是否激活"（**不要等 info 行**）

### 4.1 判据（从强到弱）

1. **stderr 是否干净**：激活后 stderr **0 字节**（无 pending / failed / warning）。
   反证：只要没激活，stderr **一定**有诊断（见 §3）。这是本次验证使用的主判据。
2. **板文件是否被创建**：`<DSH_HOME>\team\team.db` 存在、WAL 开启、`schema_version=4`、表齐全
   （`task/evidence/dispatch/event/ack/cursor/...`）。插件 README 的判据原文：
   "板文件不存在 → 装完要重启 DSH，apply() 才会被执行" —— 反过来，**板文件存在 ⇒ apply() 跑过**。
3. **只读验收脚本**：对隔离 profile 跑 `node tools/verify.mjs`（或等价脚本），本次结果
   **16 项 15 通过、1 项预期失败**（失败项是"事件表有内容"，隔离实例没有对端事件，和工具注册无关）。
   通过项含：源/装 sha256 5/5 一致、profile dependencies/bundles 已登记、schema 4/表齐全/WAL。

### 4.2 为什么 `已加载：13 个工具` 这行看不到（观测限制，不是没加载）

插件加载时有一条 info 日志：

```
[dsh-team-mesh] 0.4.0 已加载：13 个工具，板=…
```

但在 **CLI / headless 启动方式下它不会出现在 stdout/stderr**：

- `dsh-app-boot` 只把 **warn/error** 级诊断收集成启动诊断并导出（其 exporter 过滤 `type === 'warn' || 'error'`）；
- cordis 的 **info 级在 CLI 下没有 console exporter**。

因此：**不能**用"看不到这行"推断插件未加载。反过来，因为 pending/failed 一定走 warn/error 诊断，
"stderr 0 字节"是可以作为"已激活"的判据的。本次 host-check 也是据此下的结论。

### 4.3 工具注册到哪一层

`apply()` 里的 13 次 `ctx.tools.register()` 在最后那条 info 之前执行；任何一次抛错都会进 apply 的 catch
并 `logger.error`（error 会被导出到 stderr）。所以：

- **能说**：spec 实测 13 个 + `apply()` 完整跑完（register 未抛错）= **装配层 + 激活层**；
- **不能说**：宿主工具注册表里真的有 13 个、模型侧工具目录里能看到 —— 本次没有注册表导出、也没有模型调用，
  这一层**未直接观测**（边界见 §9）。

## 6. 常见坑（PowerShell 5.1 / 随机端口 / 证据脱敏）

1. **`&&` 不可用**：PowerShell 5.1 用 `;` 或分行；条件执行用 `if`。
2. **JSON body 编码**：`Invoke-RestMethod -Body (ConvertTo-Json ...)` 直接传字符串时，PS 5.1 会按默认编码
   发送，中文/特殊字符容易乱。用 `[System.Text.Encoding]::UTF8.GetBytes($json)` 传字节，并显式
   `-ContentType 'application/json; charset=utf-8'`；`ConvertTo-Json` 记得 `-Depth`。
3. **PS 5.1 没有 `-SkipHttpErrorCheck`**：非 2xx（如 429/409）会抛异常；用 `try/catch` 从
   `$_.Exception.Response` 读状态码与 body（或改用 `Invoke-WebRequest` + `-UseBasicParsing` 的响应对象）。
4. **随机端口**：宿主用 `--port 0`，实际端口看 stdout；板服务随机高位端口（如 50541）或 `PORT=0`，
   **不要撞** 13090 与在用端口。
5. **token / URL 脱敏**：宿主 stdout 的 web URL 带访问 token；板 token 随机生成。
   证据里一律 `token=<redacted>`，板 token 不写进日志/报告/仓库。
6. **中文乱码**：PS 控制台显示 UTF-8 日志可能乱码，文件本身是 UTF-8；用
   `Get-Content -Encoding UTF8` 或 node 读，别据此判断写入失败。
7. **清理**：停掉隔离宿主与临时板（`Stop-Process` / Ctrl-C）、确认端口 closed、删除隔离 DSH_HOME
   与临时库/日志/tmp（里面的 token 文件一并删）。**别删在用 profile 或生产目录。**
8. **红线**：不碰在用 profile / 在跑 DSH 进程 / 生产板 13090；隔离实例里**不要放真实模型凭据**，
   本次验证全程没有模型调用。
